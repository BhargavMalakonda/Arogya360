## 1. Cross-Validation Report

**Verdict: Architecture is sound and ready for execution — with 4 fixes required TODAY before any code is written.** These are not redesigns; they are decisions your four modules left open or let drift, and an agent will guess wrong if you don't lock them first.

### ✅ What's confirmed working
- **Diagnostic hallucination is genuinely separated from triage.** The symptom→disease dictionary bounds Gemini to a candidate list, the deterministic ESI rule table stops the LLM from "vibing" a severity score, and ESI-1 bypasses the AI entirely via hard-coded keyword detection. A judge asking "what stops your AI from hallucinating a rare disease" has a real, specific answer — this is your strongest defensible claim.
- **Prevention tips and government schemes are correctly de-risked.** Both are pulled from static backend JSON (`prevention_kb.json`, `schemes.json`) keyed off `symptom_category`/`risk_level`, never generated by Gemini. This is the single best decision in your whole spec set — it removes hallucinated medical advice and hallucinated scheme names as a demo failure mode entirely.
- **API keys are correctly isolated.** Gemini key never touches the frontend (FastAPI-only, verified via Firebase ID token). Maps key is frontend-restricted by HTTP referrer and called via the JS SDK, not raw REST — this avoids the exact class of "worked locally, broke on deploy" bug your team already got burned by once.
- **The continuity loop is real.** Follow-ups live inside `assessments` (no extra collection, one composite index) and Community Insights uses `getCountFromServer()` with a privacy floor (suppress if n<3) — both cheap, both defensible, both directly answer the Problem Statement's "community-facing" and "sustainable" requirements.
- **Voice and Follow-ups need zero backend work.** Web Speech API and Firestore client queries mean Techie D's Phase 6 work is pure frontend — one less thing that can break on a Render cold-start during the live demo.

### 🔴 Fix #1 — The UI mockups depict a different product. Do not build toward them literally.
The AuraMed screenshots show an **enterprise clinician CDSS**: differential diagnosis with confidence percentages, an Rx/formulary generator, live tele-consultation, EMR/ABDM/FHIR compliance badges, a "diagnostic reasoning chain" drawer. None of this exists in Module 3's actual 4 golden-path screens (Auth, Home, Triage MCQ, Result), and several pieces of it are things your Doctor **cannot** defend for this Problem Statement — a hackathon self-triage tool prescribing medication or showing "94.2% AI Confidence" on a diagnosis is a credibility and safety liability, not a flex.
**Decision, locked now:** the screenshots are a **visual style reference only** — glassmorphism cards, gradient buttons, spacing, iconography. Claude Code will be explicitly instructed to reskin Module 3's actual screens in this aesthetic, and explicitly forbidden from building any CDSS/Rx/tele-consult/EMR feature from the mockups. This goes in `claude.md` (Section 3 below) as a hard rule.

### 🔴 Fix #2 — Color palette conflict between Module 3 and the mockups.
Module 3 defines a flat clinical palette (`#2563EB` primary, `#DC2626` emergency, etc.) for ESI risk badges. The mockups use a purple/indigo glassmorphism gradient theme. **Decision:** adopt the glassmorphism *aesthetic* (nicer demo, more "AI-native" feel) for the overall shell, but the **ESI risk badge colors are locked to Module 3's exact mapping** (red/orange/green) regardless of overall theme — color-coded medical risk must stay conventional, not on-brand. Non-negotiable; a judge or the Doctor will notice if "high risk" isn't red.

### 🔴 Fix #3 — Question-count and MCQ-vs-chat guidance contradicts itself across your own notes.
Your AI Engine notes first say "exactly 4 questions," then explicitly reverse to "3–6 targeted, hard cap 6." They also land on a **hybrid** flow (one open-text initial complaint, then strict MCQ) after initially proposing pure open chat.
**Decision, locked now:** `MAX_QUESTIONS = 6`, `TARGET_QUESTIONS = 3–5`, flow is **hybrid** (free-text initial symptom → keyword-matched into the disease dictionary → Gemini asks 3–6 bounded MCQ questions, using SOCRATES sub-flow specifically when the initial complaint is pain-type). This must be written into the Phase 3 Kiro prompt verbatim so it isn't reinterpreted mid-build.

### 🔴 Fix #4 — The `assessments` schema is missing a field your own scheme-injection design requires.
Module 2's schema (the authoritative one, v3.0) has no `government_resources` field, but the AI Engine notes and Module 3's Result screen both require displaying injected schemes. **Fix now:** add `"government_resources": []` to the `assessments` schema (array of `{scheme_name, benefit, link}` objects, backend-injected, never Gemini-generated). This is a one-line schema patch — do it before Kiro writes Phase 3, or the Firestore document Kiro writes and the document Claude's Result screen reads will disagree.

No other fatal flaws found. Firestore security rules across Module 2 and Module 4 are consistent (Module 2's early looser `write` rule was already self-corrected to `create`-only in the same doc — Module 4's version is authoritative, use it verbatim). Proceed to build once Fixes #1–#4 are acknowledged by the whole team.

### **Phase 3 — AI Engine (To Kiro)**

```
Implement the triage AI engine for Arogya360. This is the most safety-critical part of
the system — follow every rule below exactly, do not simplify.

LOCKED DECISIONS (do not deviate):
- MAX_QUESTIONS = 6, TARGET_QUESTIONS = 3-5
- Flow is hybrid: user free-types their initial complaint once, then the system asks
  only bounded multiple-choice questions
- ESI-1 NEVER comes from Gemini — it is a hard-coded pre-check that bypasses the LLM
- Gemini NEVER writes prevention tips or government schemes — those come only from
  static backend JSON lookups
- The assessments schema below is the single source of truth — do not add or rename fields

STEP 1 — Static data files (populate these in app/data/):
- disease_dictionary.json: keyword → candidate disease list, using exactly this map:
  {"fever": ["Dengue","Malaria","Viral Fever","Pneumonia"], "cough": ["Tuberculosis",
  "Pneumonia","Asthma"], "thirst": ["Diabetes"], "urination": ["Diabetes"],
  "headache": ["Hypertension","Dengue","Viral Fever"], "dizziness": ["Hypertension",
  "Diabetes","Anaemia"], "breathlessness": ["Asthma","Pneumonia","Tuberculosis"],
  "chest_tightness": ["Asthma","Pneumonia"], "body_pain": ["Dengue","Malaria",
  "Viral Fever"], "fatigue": ["Diabetes","Tuberculosis","Anaemia","Malaria"]}
- esi_rules.json: encode the full deterministic ESI-4/ESI-3/ESI-2 rule table for all
  8 diseases (Tuberculosis, Diabetes, Hypertension, Dengue, Malaria, Pneumonia, Asthma,
  General Viral) — I will paste the full table content into this conversation for you
  to transcribe faithfully; do not invent thresholds.
- prevention_kb.json: keyed by symptom_category (respiratory, metabolic, cardiovascular,
  general, etc.) with 3-5 verified prevention tips per category, sourced from WHO/ICMR/
  MoHFW guidance style language (generic lifestyle advice only — no medication names,
  no dosages).
- schemes.json: a small list of REAL Indian government health schemes only (e.g.
  Ayushman Bharat PM-JAY, eSanjeevani, Jan Aushadhi, National TB Elimination Programme)
  with {scheme_name, type, eligibility_note, benefit, link}. Do not invent scheme names.

STEP 2 — Emergency Engine (runs BEFORE anything else, on every message):
- Hard-coded keyword list (case-insensitive substring match) for immediate ESI-1:
  severe breathlessness, blue lips, cyanosis, unconscious, unresponsive, confusion,
  coughing blood, severe chest pain, unable to speak in full sentences
  [Doctor-confirmed final list — do not add or remove without sign-off]
- If matched: skip Gemini entirely, return
  {"risk_level": "ESI-1", "emergency": true, "message": "This may be a medical
  emergency. Seek immediate help.", "recommended_action": "Call emergency services
  or go to the nearest hospital emergency department now."}

STEP 3 — POST /api/triage/start (protected via get_current_user):
- Input: {"initial_symptom": "<free text>"}
- Run Emergency Engine check first (Step 2)
- If not emergency: keyword-match initial_symptom against disease_dictionary.json to
  get candidate_diseases list (fallback to ["General Viral / Other"] if no match)
- Construct a Gemini prompt that:
  - States the candidate disease list and FORBIDS considering diseases outside it
  - Instructs Gemini to ask ONE multiple-choice question at a time (fields:
    question, options[], clinical_hint) aimed at differentiating within the candidate
    list, using SOCRATES sub-questions specifically if the initial complaint is pain-type
  - Returns strict JSON only (no prose)
- Call Gemini, return its first question + the candidate_diseases list + a
  conversation_id (can be a simple UUID, no Firestore write yet)

STEP 4 — POST /api/triage/next (protected):
- Input: {"conversation_id", "history": [...], "candidate_diseases": [...]}
  (history is the full running transcript, sent by frontend each time — see "Hybrid
  State" pattern: NO Firestore reads/writes happen mid-conversation, only in-memory
  transcript passed back and forth)
- If len(history) >= MAX_QUESTIONS (6): stop asking questions, move to STEP 5 (final
  assessment) instead of asking another question
- Otherwise: call Gemini with the running history, bounded to candidate_diseases,
  get the next question, return it (same shape as Step 3)
```
